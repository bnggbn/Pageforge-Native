# 版本讀取與差異儲存評估

## 現在的行為

正式保存與還原都追加 VAX 節點。還原會把指定舊版的文字／筆記作為新節點內容，保留所有既有節點與 original 檔。畫面切換版本或查看 diff 不改寫磁碟；還原內容需要明確按「還原所選版本為新版」。尚未提交的文字草稿仍保留，不會被還原操作覆蓋。

Windows 正常關閉會攔截 WM_CLOSE：有文字／筆記草稿、尚未保存的布局或位置時，提供保存、捨棄目前草稿、取消。保存文字與筆記為可續寫草稿，不自動新增正式 VAX 節點；外觀工作室的保存則套用有效外觀 JSON。捨棄只刪除目前草稿，透過草稿 token 檢查並行衝突，保留其他草稿及已提交版本；布局與閱讀位置仍保存。保存失敗或文件正在提交時，留下視窗。強制結束程序、斷電及作業系統強制關機不保證走此提示。

## 已落地的效能與讀取保護

- Native 讀書與提交用 view=reader 投影：只傳目前完整版本、revisionCount 及歷史摘要。舊草稿需要另一基準時，按 ID 取得一份已驗證快照。原有完整歷史 HTTP 回應保持相容。
- Go 只保留最近一本、容量內的已驗證歷史快取。每次仍串流 SHA-256 原檔與全部版本位元組；相同內容才重用解碼結果與 VAX 驗證結果，不能用恢復 mtime 或相同檔案大小繞過驗證。快取不落盤，也不改變 VAX 或書庫 schema。呼叫端取得可變切片的副本。
- 快取未命中（首次讀取、重啟、切換至其他書、新版或外部修改）仍解碼及完整驗證。快取識別的是實際交給驗證器的位元組，避免讀取期間外部變更造成錯誤快取。
- 共用父目錄每次檢查一次，逐版仍檢查檔案不是連結、是一般檔案且符合容量。
- collection 同步在一次鎖定內建立一次原檔雜湊／格式索引，新增後更新索引；同批與下次重複來源都去重，不再逐檔掃描整書架與排序。
- HTTP 包含完整回應串流的單一 deadline，逾時或超量取消請求與訂閱。JSON 紀錄、原檔、整本歷史、草稿總量及數量都有讀取限制。這是本機資源保護，不代表完成第三方套件漏洞掃描。

設定可在 pageforge.config.local.json 覆寫，舊設定省略新增群組時套用預設：

| 設定 | 預設 | 用途 |
| --- | --- | --- |
| storage.recordMiB | 64 | manifest、單份 snapshot／draft 的 JSON 位元組上限 |
| storage.historyMiB | 256 | 一次讀取的原檔與全部版本總量；草稿集合也用此總量上限 |
| storage.verifiedCacheMiB | 64 | 快取歷史的序列化容量門檻；0 停用，Go 物件管理另有額外成本 |
| transport.requestTimeoutMs | 30000 | 書庫請求的標頭與完整回應共用期限 |
| transport.responseMiB | 64 | Native 書庫 HTTP 回應上限，包含無 Content-Length 的串流 |

原檔另受 limits.documentMiB（預設 20）限制；閱讀位置限 16 KiB。外觀 HTTP 回應限 1 MiB、整體 10 秒；外觀持久檔仍沿用原本 16 KiB 限制。線索牆沿用 evidenceWall.layoutMiB（預設 4）。歷史／草稿超量明確拒絕，不裁掉歷史；超量或無效的閱讀位置則忽略。較大的既有書庫可調整設定後載入。

暖快取 benchmark 使用暫存書庫、每版 64 KiB，先完成一次驗證，再用 go test ./internal/library -run '^$' -bench BenchmarkWarmLoadHistory -benchtime=5x -benchmem 測量。與保留的舊後端副本序列執行 500 版對照，當次數據如下：

| 500 版 × 每版 64 KiB | 時間／次 | 累計配置／次 | 配置次數／次 |
| --- | --- | --- | --- |
| 原本完整解碼與驗證 | 1.768 秒 | 132.0 MiB | 249033 |
| 新版暖快取 | 1.365 秒 | 1.16 MiB | 7142 |

累計配置不是峰值記憶體或 RSS，不包含 HTTP／Dart。暖快取數據不代表冷讀取、提交後或超過快取門檻的成本。Windows I/O 耗時受背景建置及檔案掃描影響大，不據此宣稱固定加速倍數。

仍待解決：整條歷史的檔案 I/O、冷讀取與新增版本後的完整驗證、歷史摘要分頁、大型 JSON 的 isolate 解碼。現有快取與精簡回應改善重複工作及記憶體，尚未使歷史讀取成為固定成本。

## 是否改成 Git 式差異儲存

建議保留「邏輯上不可變快照」，下一階段把實體內容改成可去重的內容定址物件。Git 的邏輯模型也是快照；實體 packfile 才會用差異壓縮。[Git 快照模型](https://git-scm.com/book/en/v2/Getting-Started-What-is-Git%3F)、[Git packfiles](https://git-scm.com/book/en/v2/Git-Internals-Packfiles)。

| 方案 | 空間與讀取 | 適合程度 |
| --- | --- | --- |
| 現有每版 JSON 完整文字與筆記 | 直讀容易，但筆記新增也重複存整文 | 本次維持相容 |
| 內容定址、壓縮 blob | 文字／筆記分開去重；相同內容不重複寫入，可直接取任一版 | 建議先做的實體儲存改版 |
| 相鄰版本只存文字差異 | 小修改省空間，但讀舊版／校驗要還原鏈；刪壞基底影響後續 | 不建議無限串接 |
| blob 加有界 delta pack 與完整 checkpoint | 控制解碼深度並節省大量相似文字的空間，實作與驗證較複雜 | 去重量測後再做 |

實作前應完成下列合約及遷移驗收；本次未啟用新儲存 schema：

1. VAX 的 contentHash／notesHash 始終對「還原後完整內容」計算；事件、ID、SAI、envelope 與既有 canonical bytes 不變。物件去重不能修改原始 VAX 歷史。
2. immutable blob 以強雜湊辨識；先寫物件再原子發布索引。文字與 notes 分開，筆記版本可共用同一文字物件。原始來源檔仍保留。
3. legacy JSON 讀取器保留；遷移寫到新目錄，逐版還原、驗證、比對完整內容與 notes，再發布新索引並保留原檔備份。失敗可直接回到舊索引。
4. delta 只在壓縮收益達門檻時使用；設定最大還原深度（例如初期 16）、單物件及還原後總量上限。遇到 checkpoint 直接還原，不讓版本數決定最壞讀取深度。
5. 儲存 diff 與畫面 diff 分開；不要拿有 deadline、可能省略結果的 UI 比較輸出當唯一恢復資料。UTF-8、中文／emoji、空行、檔尾換行及筆記變更均需精確往返測試。
6. 故障注入涵蓋缺失／竄改基底、循環依賴、解壓超量、崩潰於各發布階段、GC 保留被 draft／branch／restore 引用物件。先量測大型真實形狀的合成歷史，再選 checkpoint 間隔。

差異儲存能減少硬碟重複內容，但無法單獨消除 API 傳整份歷史、重複 VAX canonical 化或畫面重建；這些必須各自改善。

針對百萬字文件，整文 blob 去重不足以降低持續改字的成本；後續需操作模型、分塊共用與有順序的樹索引。復原日誌不進正式 VAX，既有全文雜湊與未來樹根的協定界線見 [分層保存與大型文件](LARGE_DOCUMENTS.md)。此方案尚未實作。

## crash 後的定時草稿復原

定時保存可與增量儲存搭配，提供最後落盤點的復原能力。先補持續輸入時的最大保存等待與請求合併，再加入完整 checkpoint 加可驗證增量日誌；正式版本歷史仍由明確保存建立。排程、候選配置、損壞尾端、重開選擇、失效鎖與崩潰注入驗收見 [定時增量草稿復原](DRAFT_RECOVERY.md)。此部分目前是規劃，現有 runtime 仍為停筆防抖保存完整草稿。
